# 🌸 花园复活追踪 · flower-tracker

一个**单文件、零构建、零后端**的网页小工具，用来为多个游戏账号批量管理花朵的「枯萎倒计时」，
并把珍稀花的收集进度量化成可预估的天数。

所有逻辑（React 组件、状态、解析器、存储）都写在同一个 `.html` 文件里，
双击即可运行，不需要 npm / 打包 / 服务器。

## 快速开始

1. 双击 `flower-tracker.html`，用 Chrome / Edge / Firefox 打开。
2. 点右上角 **「+ 添加账号」** → 把游戏里的花朵记录粘进输入框 → 点「导入」。
3. 之后每次登录前扫一眼卡片上的倒计时，在花朵枯萎前点 **「复活」** 即可重置该花的计时。
4. 备份 / 换设备点 **「💾 备份同步」**：可导出 JSON、生成分享码，也能从文件或分享码导入。

> 首次打开需要联网：React 18、Babel Standalone、lz-string、Google Fonts 都走 CDN。

## 功能清单

### 1. 账号卡片

- **排序规则**（依次生效）：
  1. 被**置顶**的账号永远排第一；
  2. 所有花都还是「未记录」的新账号排在前面；
  3. 其余按**最紧急的那朵花**（剩余时间最短）升序——标了「不着急」的花种**不参与**这个计算，
     所以整个账号只剩不着急的枯萎花时，它会沉到还有急事的账号后面。
- **置顶**：点任意花朵的 **⚙** 会把该账号置顶（用于临时盯住某个账号），账号 ID 旁出现可点击的 **📌 已置顶** 标签，
  点它或在页面**空白处**单击即可取消。置顶状态写进 `xhx-pinned-account`，刷新和导入导出都会保留
  （点按钮 / 输入框不会误取消）。
- **账号 ID 按钮**：单击复制到剪贴板（显示 ✓ 反馈）；**长按 600ms** 进入重命名。
  重命名会同步迁移提醒开关、折叠、置顶与提醒状态缓存。
- **状态胶囊**：`全部枯萎` / `部分枯萎` / `即将枯萎` / `未记录`，以及开启提醒后的 🔔。
- **头部双击空白处**：开关该账号的枯萎提醒（纯页面内提醒，不申请浏览器通知权限）。
- **折叠**（▼/▲，悬停才显示）：折叠后默认不显示，用于把不常看的账号收纳起来。
- **全部复活**：一键刷新该账号下**所有**花的计时（包括还活着的），并累计今日复活额度。
- **删除账号**：两步确认（「删除账号」→「确认删除」），同时清理该账号的提醒、折叠与置顶记录。

### 2. 花朵行

- **状态圆点**：三档呼吸灯动画 —— 已枯萎 `pulse-red`(1.5s) / 24h 内即将枯萎 `pulse-orange`(2s) / 正常 `pulse-green`(3s)。
- **倒计时**：数字用 `AnimatedNumber` 做 rotateX 翻牌过渡；每 20 秒全局重算一次。
- **枯萎时刻**：`复活时间 + 存活时长`，显示为 `MM-DD HH:mm 枯萎`。
- **双击花名重命名**：内联输入，格式 `花名+数量`（如 `黑色罗布麻36`），Enter 保存 / Esc 取消。
- **✕ 删除此花**（悬停才显示）。
- **⚙ 修改倒计时设置**：见下。
- 花朵行排序：剩余时间升序，「未记录」排最后；同一账号花朵种类 **> 8** 时默认只显示前 8 种，出现「展开 (N种)」按钮（展开状态刷新后重置）。

### 3. 修改倒计时设置（⚙ 弹窗）

两个输入框**双向联动**：

| 字段 | 说明 |
| --- | --- |
| 复活时间 | `datetime-local`，允许手动填一个**过去**的时间来修正记录 |
| 存活时长 | 文本框，支持 `3.5`（3.5 小时）或 `3 30`（3 小时 30 分）两种写法 |

改任一个，另一个立刻联动重算。默认时长 `336h`（14 天）。

### 4. 导入面板（+ 添加账号）

左右两个输入框并存，可同时填写，导入时会合并：

- **格式1（无剩余时长）**：每行 `花名+数量 ... 账号ID`，导入后状态为「未记录」。
- **格式2（带剩余时长）**：花行 `花名+数量 小时 分钟`，账号 ID **单独一行**；
  导入即算出已过去的时长，直接进入倒计时状态。
- 格式1 的输入框里**只要含 `#` 号**，也会自动切换到「新格式」解析（等价于格式2，账号 ID 单独一行，`#` 单独一行会被忽略）。
- 「查看格式说明 ▼」里有折叠的格式提示。
- 同一账号重复导入：按**花名去重**合并，已存在的记录不会被覆盖。

### 5. 近 14 天枯萎日历

吸顶面板下方的可折叠面板（绝对定位下拉，`scaleY` 弹出动画）：

- 横轴 14 天，**今天**的柱子只画「今天这一批」：下层「已复活」（绿）+ 上层「今日枯萎」（橙，
  枯萎时刻在今天 00:00–24:00 内，含今天稍后才会枯的）；今天这批超过 30 时柱子描红框。
  「更早积压」（今天之前就枯的）不进柱子，只显示在概览行文字里。
  未来某天只显示当天枯萎总数（≤30 淡黄 / >30 淡红）。
- 时间轴上方有一行今日概览：`今日枯萎 N 棵 · 其中未复活 K 棵 · 更早积压 M 棵`，今天这批超过 30 时
  追加红字「今日已超额」（悬停 `?` 看口径）。今天已复活多少看标题栏的「今日额度 R/30」，两处不重复显示。
  **「今日枯萎」是当天 00:00–24:00 的枯萎总数，复活了也不减**（复活会在覆盖倒计时前记住它原本是不是
  今天枯的）；因为已复活里可能包含更早积压的花，柱子的 绿+橙 不一定等于「今日枯萎」。
- 柱子以 **30 朵**为满格；单日超过 30 朵时按比例填满。所以 30 也是隐含的「每日复活额度」。
- 角落显示 `待处理 N 朵（今日额度 3/30）`。
- **搜索框会同时驱动日历和列表**：

| 搜索内容 | 行为 |
| --- | --- |
| 空 | 显示全部（不含折叠账号） |
| 纯数字 | 按账号 ID 过滤，日历标题变成 `📅 账号 #1024 枯萎日历` |
| `//` | **只显示折叠中的账号**，日历标题变成 `📅 折叠账号枯萎日历` |
| 其他文字 | 按花名模糊匹配，标题变成 `📅 "紫" 枯萎日历` |

### 6. 收集进度（📊 悬浮球）

右侧悬浮球打开的面板，用来把「还差多少朵」变成「还差多少天」：

- 每条目标显示：`已有 / 需要`、进度条（>50% 橙 / 完成绿 / 未设置灰）、`预计 N 天`，以及 `单色+双色` 数量徽标。
- 表头 `📊 收集进度` 旁的 **`?`** 点开就是预计天数的口径说明（下面这段的简版），不用去翻文档。
- **排序**（选择结果会记住）：进度从低到高 / 从高到低 / 首字母 A-Z / Z-A / 预计最早完成 / 预计最晚完成。
- **不着急标记**：每行右侧的「不着急」按钮按花种打标（跨账号同名生效）。打了标的花在**所属账号内
  沉到最下面**（组内仍按剩余时间排），同时**不参与账号排序的紧急度计算**（只剩不着急花的账号会沉后）。
- **只看不着急**：打过标后，顶部搜索框旁会出现「不着急 N 种」开关，点一下整个列表只显示这些花
  （跨账号聚在一起，方便批量复活），再点一下恢复。只是视图过滤，**任何统计数字都不变**，也不会记住
  —— 下次打开恢复完整列表。
  只影响排序，**不影响任何统计数字**。
- **增删改**：`+` 添加目标（输入花名时从珍稀花列表智能联想）、`✏️` 编辑、勾选后 `🗑` 批量删除。
- **一键添加所有珍稀花**：把 22 种珍稀花全部建成目标，默认需要 100 朵。
- 点「复活」时，珍稀花（含双色花拆分后的份额）会自动累加到 `owned`。

**预计天数怎么算：**

```
窗口内可获得朵数 = 单色花枯萎总数 × 100%
                 + 双色花枯萎总数 × 50%
                 + （昙花额外 × 7）
每天平均 = min(窗口内可获得朵数 ÷ 14, 30)     ← 30 即每日复活额度
预计天数 = ceil((需要 - 已有) ÷ 每天平均)
```

「窗口」= 从今天到第 14 天（**含第 14 天**）——因为默认存活时长 336h 正好 14 天，刚复活的花枯萎日就落在第 14 格。窗口若不含第 14 天，这些花会从分母里消失，导致「复活后进度增加、预计天数反而变长」。

**每天平均要按每日额度封顶（30）**：游戏规则是一天内前 30 株复活的枯萎花各奖励 1 朵，超出的只复活、不奖励，所以供给再多也只能按 30/天 转化。供给不到 30/天 时封顶不生效；供给饱和时吞吐恒为 30/天，「剩余 ÷ 30」正好是精确解，不是近似。常量在 `DAILY_QUOTA`。

昙花单独乘 7，是因为它的周期是 48 小时，14 天里会枯萎 7 轮。

> **这是乐观口径**：相当于假设这段时间的复活额度都只花在这一种花上。额度实际是全局共享的（`xhx-today-revived` 是单一计数器，不分花种），所以同时推进多个目标时它们会互相争额度，实际天数会比显示的更长。收集面板表头的 `?` 里有同样的说明。
>
> 另外这个估算用的是「未来能收到多少」而不是「过去收得多快」，所以复活当下的预计天数会随花园所处周期上下浮动，不代表你的实际收集速度在变化。

### 7. 备份与同步（💾 备份同步）

顶部的「💾 备份同步」按钮打开一个面板，把四件事集中在一起：

**⓪ 导出范围（文件与分享码共用）**

三选一：**全量 / 仅账号 / 仅设置**，「导出为 JSON」和「生成分享码」都按它走。「仅设置」只带主题 / 排序 / 提醒 / 折叠 / 置顶，导入时只能走「只导入设置」。

**① 文件备份**

- **导出为 JSON**：写出**信封格式 v2**，文件名带范围与时分（`花园复活追踪备份_全量_2026-09-15_11-30.json`），同一天多次导出不会互相覆盖。
  备份内容除账号与花朵外，还包含**收集目标、提醒开关、折叠账号、收集排序、主题、置顶账号**；完成后提示里带体积（约多少 KB）。
- **从文件导入**：读完文件后不直接落库，而是弹出三选一。
- **账号多时首选这条路**：文件不受长度限制，手机上用微信/QQ 的「发送文件」传给自己就行。

**② 分享码（跨设备粘贴同步）**

- **生成分享码**：把选中的备份用 LZ-String 压缩成一段文本（是原始 JSON 的约 **30%**），一键复制；生成后会显示**字符数**。
- ⚠️ **账号多时分享码会很长**：实测 145 账号 × 5 种花 ≈ **14,600 字符**、× 20 种花 ≈ 44,000 字符（二维码单张上限才 2953 字节，所以**做不了二维码**）。超过 3000 字符面板会提示改用文件导出——微信/QQ 里粘贴这么长的文本容易换行或被截断。
- 分享码现在的合适场景是「**仅设置**」这类小体积搬运（几百字符）。
- **导入分享码**：粘贴到另一台设备即可，粘贴时多余的换行空格会被自动清掉。粘贴「仅设置」码时弹窗只显示「只导入设置」一个选项。
- 压缩库加载失败会**降级为 base64**（码会变长约 1.45 倍），功能不受影响。

**③ 三选一导入策略**

| 策略 | 账号与花朵 | 收集目标 | 偏好设置 |
| --- | --- | --- | --- |
| 🔀 **合并导入** | 按 `accountId` 合并，花朵按 `name` 去重（已存在的不覆盖） | 同名取 `needed` / `owned` 的 **max**，不相加 | 与现有设置**取并集** |
| ♻️ **覆盖导入** | 整体替换 | 整体替换 | 以备份为准 |
| ⚙️ **只导入设置** | 完全不动 | 完全不动 | 以备份为准 |

三种策略都会把偏好里指向**不存在账号**的记录过滤掉。`owned` 取 max 而不是相加，是因为两台设备记的是同一批真实花，相加会翻倍。

**④ 自动快照**

- 每次改动账号数据前，自动把**改动前**的状态存一份，滚动保留**最近 3 份**（`xhx-autobackup-v2`）。
- 面板里列出快照的时间与规模，点「恢复」即可回退；单份超过 500KB 会跳过，避免撑爆 localStorage。
- 导入 / 恢复操作也会先留一份快照，所以误操作后有后悔药。

**向下兼容**：旧版导出的**裸数组** JSON 仍可导入，会被识别为 v1 并在弹窗里标注「旧版备份，仅含账号数据」。

> ⚠️ 它和上面「+ 添加账号」里的粘贴导入是两套逻辑：粘贴导入只合并账号与花朵，不碰偏好设置。

### 8. 其他细节

- **主题切换**：🌙 深色 / ☀️ 浅色，记忆在 `xhx-theme`，默认深色。深浅色各自有独立的卡片/边框/状态色/滚动条配色。
- **回到顶部**：滚动超过 300px 出现的毛玻璃圆钮；它出现时 📊 悬浮球会自动上移避让。
- **回到刚改的账号**：复活 / 编辑 / 添加 / 删除花朵 / 改账号ID后，左下角浮出 `↑ 回到 #账号ID` 胶囊（最多记 3 个，
  最近的排最前），点一下滚到该账号并高亮 2 秒、卡片挂上「刚刚修改」徽标。只存在于当前会话，刷新即清空。
- **今日统计**：`xhx-today-revived` 与 `xhx-revived-today-ids`，每天自动归零（每 60 秒检查一次跨天）。
- **控制台调试接口**：`window.__debugAccounts`（当前账号数组）。

## 数据模型

```js
// localStorage["xhx-tracker-v1"]
[
  {
    id: "a1b2c3d",                 // 内部随机 id
    accountId: "1024",             // 账号 ID（建议纯数字）
    flowers: [
      {
        id: "e4f5g6h",
        name: "黑色罗布麻",         // 花名，可能带前导数字前缀
        count: 30,                // 数量
        revivalTime: 1757900000000, // 本轮「复活」时刻；null = 未记录
        durationMs: 1209600000      // 存活时长，336h = 14 天
      }
    ]
  }
]
```

### 备份文件（信封 v2）

```json
{
  "_app": "flower-tracker",
  "_version": 2,
  "_exportedAt": "2026-09-15T03:30:00.000Z",
  "accounts": [ /* 同上的账号数组 */ ],
  "collectionGoals": {
    "黑色罗布麻": { "needed": 100, "owned": 30 }
  },
  "prefs": {
    "theme": "dark",
    "collectionSort": "nameDesc",
    "accountReminders": ["1024"],
    "collapsedAccounts": ["2048"],
    "pinnedAccount": "1024"
  }
}
```

- `_app` 用于识别文件归属，不是本工具的备份会被拒绝。
- `_version: 1` 或**直接是数组**都按旧格式处理（只有 `accounts`）。
- 今日额度 `xhx-today-revived` / `xhx-revived-today-ids` 与自动快照**刻意不写进备份**。

推导公式：

```
枯萎时刻  = revivalTime + durationMs
剩余时间  = 枯萎时刻 - now          （remMs）
状态      = 剩余 ≤ 0        → wilted（已枯萎）
            剩余 < 24h      → urgent（即将枯萎）
            其余            → alive（正常）
            revivalTime 为 null → unknown（未记录）
```

常量：

| 常量 | 值 | 含义 |
| --- | --- | --- |
| `DEFAULT_MS` | `336 * 3600 * 1000` | 默认存活 14 天 |
| `EPHEMERAL_MS` | `48 * 3600 * 1000` | 昙花专属 48 小时周期（花名含「昙花」即命中） |

## 导入格式详解

解析入口是 `parseInput(text, forceFormat2)`，规则如下：

```js
const useNewFormat = forceFormat2 || text.includes('#');
```

**旧格式（无 `#`，格式1 输入框）**

逐行处理：若该行**最后一个 token 是纯数字**，则视为账号 ID；
它前面的每个 token 用 `/^(.+?)(\d+)$/` 拆成 `花名 + 数量`，`revivalTime` 置为 `null`。

```
黑色罗布麻30 紫罗兰12 1024
紫色昙花2 2048
```

**新格式（含 `#`，或格式2 输入框）**

```
黑色罗布麻30 146 14
1024
紫色昙花2 20 12
紫色雪莲1 44 2
2048
```

- 单独一行的 `#` 会被跳过。
- **只有 1 个 token 且是纯数字**的行 = 账号分隔线：结算此前累积的花，归属该账号。
- 花行必须是 **≥3 个 token**，且最后两个是纯数字（小时、分钟）；
  倒数第三个 token 用 `/^(\d+)?(.+?)(\d+)$/` 拆出「可选数字前缀 + 花名 + 数量」。
- 换算：`revivalTime = Date.now() - (durationMs - 剩余时长)`，
  这样「剩余 146h14m」会立刻表现为一朵已经过去了 189h46m 的花。
- **最后一组花**在文本结尾结算，账号 ID 取最后一行（若最后一行是纯数字），否则记为 `unknown`。

**两种格式的结果会拼接后一起合并**：

- 账号 ID 已存在 → 合并花朵；
- 花朵按**花名**去重，已存在的不覆盖；
- 一份都解析不出来时给出错误提示，不会静默成功。

> 关键点：**账号 ID 必须是纯数字**（说明文案写的是「纯数字≥4位」，解析器实际只要求 `\d+`）。
> 写成 `A账号ID` 这种带字母的形式，该行会被**静默丢弃** —— 所以两个输入框的示例现在都用 `1024` / `2048`。

## 珍稀花与双色花机制

### 珍稀花清单（`RARE_FLOWERS`，共 22 种）

| 系列 | 成员 |
| --- | --- |
| 蔷薇系 | 白色蔷薇、粉色蔷薇、红色蔷薇、黄色蔷薇 |
| 黑色系 | 黑色罗布麻、黑色玫瑰、黑色茑萝花、黑色郁金香 |
| 绿色系 | 绿色梅花、绿色桃花 |
| 紫色系 | 紫色百合、紫色龙胆、紫色昙花、紫色薰衣草、紫色胭脂花、紫色夜来香、紫色鸢尾 |
| 夕雾系 | 粉色夕雾、蓝色夕雾、白色夕雾、紫色夕雾 |
| 其他 | 七彩彩虹菊 |

只有**本身就是珍稀花**的单色花，以及**拆分后含珍稀花**的双色花，才会进入收集统计。

### 双色花拆分表（`DUAL_COLOR_MAP`，79 条）

双色花名在统计和复活时会被拆成两种单色花名。例如：

```js
"粉白蔷薇": ["粉色蔷薇", "白色蔷薇"],        // 两种都是珍稀
"紫黑罗布麻": ["紫色罗布麻", "黑色罗布麻"],   // 只有黑色是珍稀
"蓝黑玫瑰": ["蓝色玫瑰", "黑色玫瑰"],
"七彩红彩虹菊": ["七彩彩虹菊"],              // 只有七彩是珍稀
```

除此之外还有一层兜底：`getDualColorTargets()` 会尝试**反转颜色顺序**匹配
（如 `紫黑罗布麻` 找不到时，去匹配 `黑紫罗布麻`），用 `extractColorsFromName()` 提取颜色词后排序比较。

### 复活双色花时的分配

点击双色花的「复活」，会先弹出**分配弹窗**：

- **单朵模式**：为每个珍稀目标输入分配数量，总和不得超过该花总数，剩余部分自动归为「其他颜色」（不计入收集）。
- **批量模式**（「全部复活」且含双色花时）：一次性列出所有双色花逐个分配，确认时逐个校验。

只有落在 `RARE_FLOWERS` 里的目标份额才会写进收集进度。

## 枯萎提醒机制

- 入口：**双击账号卡片头部空白处**开关该账号的提醒，成功后有 🔔 标记并持久化。
- 不使用浏览器 Notification API，**无需授权**，只在页面内提示 —— 代价是页面必须开着。
- 实现：`setInterval` 每 **10 秒**轮询一次，比较 `window.__reminderState` 中每朵花上一轮的剩余时间，触发两类事件：

| 触发条件 | Toast | 音效 | 标题闪烁 |
| --- | --- | --- | --- |
| 从「活着」跨到「已枯萎」 | 🥀 花朵已枯萎！ | 三声下行 440 → 330 → 220 Hz | `🥀 已经枯萎了！` |
| 从「> 2 分钟」跨到「≤ 2 分钟」 | 🥀 花朵即将枯萎！ | 两声上行 880 → 1100 Hz | `🥀 快去复活！` |

- 标题每 800ms 交替闪烁，30 秒后自动恢复为「花园复活追踪」。
- Toast 固定在右上角堆叠，8 秒后自动消失，可手动 ✕ 关闭。
- 音效走 Web Audio API 现场合成，无音频文件依赖。
- **只有「≤ 2 分钟」和「已枯萎」两档**，没有更早的提前预警；要提前知道只能看列表里的倒计时/日历。

### 后台运行诊断（判断最小化后会不会休眠）

备份与同步面板最底部有一块「后台运行诊断」，用于回答一个实际问题：**窗口最小化 / 手机切后台后，页面还有没有在跑？**

- 原理：另起一个 `setInterval` 每 **10 秒**记一次「相邻两次心跳的实际间隔」，统计值挂在 `window.__hb`（也方便控制台直接看）。
- 判定口径：`≤ 20s` 正常 · `20s~90s` 被降频（Chromium 对隐藏页的定时器限速，约 1 次/分钟，**没冻结**）· `> 90s` 曾被冻结（sleeping tab / Energy Saver / 系统挂起）。
- 显示内容：状态、已运行时长、上次心跳、最长间隔（含发生时刻）、冻结次数、降频次数，带「重置」按钮。
- 冻结时的提示会引导去 Edge「设置 → 系统和性能 → 始终使这些网站保持活动状态」加白名单（`file://` 时代白名单无效，换成 https 后恢复有效）。
- 统计是**会话级**的（刷新/重开清零），不持久化、不参与任何业务逻辑。

**怎么测**：打开面板 → 点「重置」→ 最小化窗口（或手机锁屏）放 20~30 分钟 → 回来看这一行。
- 显示「正常 / 被降频」→ 定时器还在跑，提醒最多晚约 1 分钟；
- 显示「曾被冻结」+ 最长间隔几分钟到几十分钟 → 冻住了，冻结期间的提醒会攒到恢复时一起补响。

## 部署到网页（手机访问）

手机浏览器基本打不开 `file://` 本地文件（iOS 几乎不可行，Android 每次要重新下载），所以要在手机上使用，需要把工具部署到一个 https 网址上。仓库自带构建脚本，产出**零外部依赖**的单文件版本：

```
node build-deploy.js 你的口令
```

| 产物特性 | 说明 |
| --- | --- |
| `deploy/index.html` | 约 310 KB 单文件，可直接托管到任何静态服务 |
| 零外部请求 | React / ReactDOM / lz-string 全部内联，**不依赖 unpkg / cdnjs**（手机弱网也能秒开） |
| JSX 预编译 | 不再需要 2.8MB 的 babel-standalone，编译在构建期完成 |
| 字体异步 | Google Fonts 改为非阻塞加载，取不到就用系统字体，**不会白屏** |
| 访问口令 | 打开页面先输入口令（存在 `sessionStorage`，关标签页后需重输）。口令是客户端校验，防路人而非防技术攻击——页面上本来就没有数据，数据都在各自浏览器的存储里 |
| noindex | 不被搜索引擎收录 |

**依赖缓存**：构建需要的 React / ReactDOM / lz-string / Babel 下载一次存在 `vendor/`（已 gitignore），之后可离线构建。`vendor/` 里任何一个文件缺失时，从对应 CDN 重新下载即可（脚本会在启动时报出缺哪个）。

**Cloudflare Pages 部署**（有 Cloudflare 账号即可，博客同款）：

1. Cloudflare 控制台 → Workers & Pages → Create → Pages → **Upload assets**，项目名建议 `flower-tracker`（决定默认域名 `flower-tracker.pages.dev`）；
2. 把 `deploy/index.html` 拖进去发布，几十秒后得到网址；
3. 以后更新：重新构建 → 在项目里替换文件重新上传。（想改成 push 自动部署也可以：把 `deploy/` 纳入版本管理，Pages 连接仓库、构建命令留空、输出目录填 `deploy`。）

**首次数据搬家（一次性）**：新网址和 `file://` 是两个隔离的浏览器存储，电脑上现有的数据不会自动过去。在旧页面「导出备份」存 JSON → 打开新网址 → 「导入备份」选**合并导入**即可。搬家之后固定用新网址，别再回旧页面记账。

**手机端建议**：Android Chrome 打开网址 → 菜单 →「添加到主屏幕」，之后像 App 一样点开；同时大幅降低浏览器清掉本地存储的概率。

## 多设备云同步（自动对齐）

在「备份与同步 → 云同步」里填 Worker 地址和同步口令即可启用。数据模型是**整份快照 + 版本号（乐观锁）**：

- 本机有改动 → 2.5 秒后自动推送到云端；云端有更新 → 本机没改动就直接采纳；
- 两边都改过（冲突）→ 弹窗让你选「用本机覆盖云端」还是「用云端覆盖本机」（选云端前本机改动会先自动快照一份，可从下方找回）；
- **每 20 秒一次轻量心跳**（`GET /snapshot?meta=1`，只问版本号，约 80 字节）——版本变了才拉全量，所以另一半改了基本 20 秒内可见，不会为了省流量把刷新拖到几分钟；另有 3 分钟一次的全量兜底；
- 页面切到后台、关闭之前会把未推送的改动先推上去（`visibilitychange` / `pagehide` / `freeze`）；
- 正在同步时被撞掉的推送会**挂起排队**，这次同步一结束立刻补推，不用干等下一轮。

三个手动按钮：

| 按钮 | 作用 |
| --- | --- |
| ⟳ 立即同步 | 先拉云端、再把本机改动推上去（双向对齐） |
| ↓ 从云端刷新 | 不看本机改动，直接用云端覆盖本机（覆盖前自动留一份快照）；卡住时点它，等价于「停用再启用」但更安全 |
| ↑ 用本机覆盖云端 | 不看云端内容，直接用本机覆盖（云端旧版本无法找回） |

状态行会写清楚**云端第几版、这份数据来自哪台设备、什么时候推的**，以及本机「上次检查 / 上次拉取 / 上次推送」各是多久前——出问题时一眼能看出卡在哪一步。

| 同步的内容 | 各设备独立的内容 |
| --- | --- |
| 账号与花朵、收集目标、**今日额度**（含今日枯萎记录）、「不着急」标记 | 主题、排序、折叠、置顶、提醒、自动快照、同步配置 |

> 今日额度必须随同步走：否则电脑复活 12、手机还能再复活 30，游戏里实际只奖励 30 朵。

**部署同步端（Cloudflare Worker + KV，免费额度足够个人用，全程面板点鼠标）：**

1. Cloudflare 控制台 → Workers & Pages → Create → Worker，起名（如 `flower-sync`）→ Deploy；
2. Edit code → 把仓库里 `sync-worker.js` 的内容整份粘贴进去 → Deploy；
3. Storage & Databases → KV → Create namespace（名字随意）；
4. Worker → Settings → Bindings → Add → KV namespace：变量名填 `SYNC_KV`，选刚建的 namespace；
5. Worker → Settings → Variables and Secrets → Add → Secret：变量名填 `SYNC_TOKEN`，值是一段只有自己知道的口令；
6. 浏览器打开 Worker 域名，看到「flower-tracker sync worker is running」即部署完成。

然后在网页的「云同步」里填：同步地址 = Worker 域名；同步口令 = `SYNC_TOKEN`；设备名可空（自动生成）。

## 已知问题与注意事项

**使用相关**

1. **首次渲染依赖 CDN**。React / Babel / lz-string / 字体都在外网，断网或 CDN 被墙时页面会白屏或停在空白。
   分享码受影响最小 —— lz-string 拿不到会自动降级成 base64，只是码会变长。
2. **Babel 浏览器内编译** → 首屏会有几百毫秒的编译延迟，且每次刷新都要重编译。生产环境应预编译。
3. **数据只在当前浏览器 profile 里**。换浏览器、换设备、清缓存都会丢，务必靠导出备份 / 分享码迁移。
4. **提醒只在页面开着的 10 秒轮询周期内触发**，关掉页面就收不到，刷新后 `window.__reminderState` 会重置（可能重复提醒一次）。
5. **「复活」会把存活时长重置为默认值**（336h / 昙花 48h），用 ⚙ 自定义过的时长会被覆盖。
6. **分享码是明文可读的**（LZ-String 只是压缩，不是加密），别把它当隐私数据的传输方式。

**代码相关**

7. **批量双色花分配弹窗直接改状态对象**（`flower.rareTargetsAllocations = ...`，输入框用 `defaultValue` 非受控），能跑通但绕过了 React 的状态流，属于脆弱写法。
8. **`_selected`（批量删除的勾选标记）会留在内存与 localStorage 里**，只在导出 / 合并时被 `stripSelected` / `mergeGoals` 剥掉。它不是持久化数据，理想做法是移出主体状态。
9. 逻辑中大量使用 `window.__xxx` 挂全局变量（长按定时器、提醒状态、轮询句柄、调试接口），多实例/多标签页共存时会互相干扰。
10. **「账号 ID」与内部 `id` 双主键并存**：备份、提醒、折叠、置顶、今日去重都以 `accountId` 为键，所以账号 ID 是事实上的主键；重命名时会同步迁移（已修），但外部若直接改 localStorage 会留下孤儿记录。
11. 没有错误边界、没有类型标注；所有样式内联，无法用 CSS 主题变量统一替换。
12. 单文件已超 180KB（未压缩源码），继续加功能建议考虑拆出构建流程。
